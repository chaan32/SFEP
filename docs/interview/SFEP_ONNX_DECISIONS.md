# SFEP ONNX 설계 결정

## Task 1 — 로컬 ONNX 개발환경과 단일 스레드

기존 가상환경이 삭제된 임시 인터프리터를 가리켜 실행할 수 없었고, 후속 모델 작업에는 버전과 네이티브 스레드 수를 확인할 수 있는 환경이 필요했습니다. 그래서 로컬에 Python 3.12 환경을 복구하고 모델 작업의 직접 의존성 버전을 고정했으며, `threadpoolctl` 컨텍스트로 계산 구간의 스레드를 하나로 제한하도록 했습니다. 대안인 전역 환경 변수는 프로세스 전체에 적용되지만, 컨텍스트는 구간을 벗어나면 이전 설정을 복구합니다. 다만 직접 의존성만 고정하므로 전이 의존성과 배포 환경 봉인은 후속 검증이 필요합니다. 검증에서는 Python과 패키지 버전, 실제 로드된 스레드 풀 제한을 확인하는 집중 테스트 3개와 `pip check`가 통과했습니다. 기존 봉인과 새 소스의 provenance가 달라지는 실패 3개는 Task 7의 재봉인 대상으로 남았으며, 최종 환경에서 전체 스위트는 다시 실행하지 않았습니다.

## Task 2 — 누출 없는 Feature 계약과 encoder

문제는 가열로 출측 시점에 사용할 수 없는 후속 공정 정보나 정답이 조인된 입력을 통해 모델에 섞일 수 있다는 점이었습니다. 또 검증 데이터를 전처리 기준에 사용하면 평가에 정보가 누출될 수 있습니다.

그래서 출측 단계까지 허용된 28개 Feature의 이름, 타입, 순서를 고정하고 나머지 열은 투영에서 제외했습니다. 전처리 계약은 전달받은 학습 행으로만 수치형 중앙값, 범주 목록, 결측 개수의 p99를 정합니다. 인코딩할 때는 중앙값 대치와 범주 원-핫을 사용하고, 각 Feature에 결측 표시를 붙입니다. 미등록 범주와 결측은 모두 `UNKNOWN`으로 처리하되 결측 표시로 구분합니다.

대안은 조인된 열을 폭넓게 사용하거나 전체 데이터로 전처리 기준을 정하는 것이지만, 출측 시점 이후 정보나 검증 정보가 섞일 위험이 있습니다. 이 선택의 트레이드오프는 허용 열과 타입을 엄격히 관리해야 하고 필요한 열이 없거나 수치형 학습 열이 전부 결측이면 실패한다는 점입니다. 결측 개수가 학습 기준 p99를 넘는 행도 별도로 표시합니다.

검증은 금지 열을 추가해도 인코딩이 같고, 학습 행 순서를 바꿔도 계약과 인코딩 바이트가 같으며, 미등록 범주·결측·라벨 가용성이 의도대로 처리되는지 테스트했습니다. 집중 테스트는 26개가 통과했습니다. 전체 Python 스위트에는 3개 실패가 남았고, 이는 Task 7의 producer provenance 재봉인 범위입니다. 각 OOF 호출이 실제로 fold train만 전달하는지는 Task 3에서, Java 교차 검증과 모델 학습은 후속 Task에서 확인합니다.
