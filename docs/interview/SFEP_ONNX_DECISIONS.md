# SFEP ONNX 설계 결정

## Task 1 — 로컬 ONNX 개발환경과 단일 스레드

기존 가상환경이 삭제된 임시 인터프리터를 가리켜 실행할 수 없었고, 후속 모델 작업에는 버전과 네이티브 스레드 수를 확인할 수 있는 환경이 필요했습니다. 그래서 로컬에 Python 3.12 환경을 복구하고 모델 작업의 직접 의존성 버전을 고정했으며, `threadpoolctl` 컨텍스트로 계산 구간의 스레드를 하나로 제한하도록 했습니다. 대안인 전역 환경 변수는 프로세스 전체에 적용되지만, 컨텍스트는 구간을 벗어나면 이전 설정을 복구합니다. 다만 직접 의존성만 고정하므로 전이 의존성과 배포 환경 봉인은 후속 검증이 필요합니다. 검증에서는 Python과 패키지 버전, 실제 로드된 스레드 풀 제한을 확인하는 집중 테스트 3개와 `pip check`가 통과했습니다. 기존 봉인과 새 소스의 provenance가 달라지는 실패 3개는 Task 7의 재봉인 대상으로 남았으며, 최종 환경에서 전체 스위트는 다시 실행하지 않았습니다.

## Task 2 — 누출 없는 Feature 계약과 encoder

문제는 가열로 출측 시점에 사용할 수 없는 후속 공정 정보나 정답이 조인된 입력을 통해 모델에 섞일 수 있다는 점이었습니다. 또 검증 데이터를 전처리 기준에 사용하면 평가에 정보가 누출될 수 있습니다.

그래서 출측 단계까지 허용된 28개 Feature의 이름, 타입, 순서를 고정하고 나머지 열은 투영에서 제외했습니다. 전처리 계약은 전달받은 학습 행으로만 수치형 중앙값, 범주 목록, 결측 개수의 p99를 정합니다. 인코딩할 때는 중앙값 대치와 범주 원-핫을 사용하고, 각 Feature에 결측 표시를 붙입니다. 미등록 범주와 결측은 모두 `UNKNOWN`으로 처리하되 결측 표시로 구분합니다.

대안은 조인된 열을 폭넓게 사용하거나 전체 데이터로 전처리 기준을 정하는 것이지만, 출측 시점 이후 정보나 검증 정보가 섞일 위험이 있습니다. 이 선택의 트레이드오프는 허용 열과 타입을 엄격히 관리해야 하고 필요한 열이 없거나 수치형 학습 열이 전부 결측이면 실패한다는 점입니다. 결측 개수가 학습 기준 p99를 넘는 행도 별도로 표시합니다.

검증은 금지 열을 추가해도 인코딩이 같고, 학습 행 순서를 바꿔도 계약과 인코딩 바이트가 같으며, 미등록 범주·결측·라벨 가용성이 의도대로 처리되는지 테스트했습니다. 집중 테스트는 26개가 통과했습니다. 전체 Python 스위트에는 3개 실패가 남았고, 이는 Task 7의 producer provenance 재봉인 범위입니다. 각 OOF 호출이 실제로 fold train만 전달하는지는 Task 3에서, Java 교차 검증과 모델 학습은 후속 Task에서 확인합니다.

## Task 3 — 시간 순서에 따른 모델 선택

문제는 미래 데이터가 학습이나 전처리에 섞이면 실제 운영 시점의 예측력을 과대평가할 수 있다는 점이었습니다. 그래서 날짜 단위의 전진 검증 세 구간을 만들고 경계를 넘는 Charge는 양쪽에서 제외했습니다. 각 구간의 전처리 계약은 학습 행으로만 맞췄고, 로지스틱 회귀, HGB, 랜덤 포레스트를 OOF 평균 정밀도 순으로 비교했습니다. 판정 임계값은 OOF F2로 선택하고 최종 모델은 가용한 참조 데이터로 학습했습니다.

대안은 데이터를 무작위로 나누거나 전체 데이터로 전처리 기준을 정하는 것이지만, 시간과 전처리 누출 위험이 있습니다. 선택한 방식은 경계의 Charge를 버리고 각 구간에 양쪽 클래스가 필요하므로 평가 가능한 데이터가 줄거나 학습이 실패할 수 있습니다. 검증에서는 날짜와 Charge 분리, 미래 범주의 전처리 계약 제외, 반복 실행의 재현성, 단일 클래스와 미가용 라벨 처리를 확인했고 집중 테스트 7개가 통과했습니다. 실제 데이터 OOF 결과는 개발 단계의 비교이며 최종 Holdout 성능이나 ONNX 적격성을 뜻하지 않습니다.

## Task 4 — ONNX 내보내기와 Holdout 평가

문제는 선택한 모델을 ONNX로 내보낸 뒤에도 확률이 유지되는지, 별도 Holdout에서 사용할 자격이 있는지 확인해야 한다는 점이었습니다. 그래서 OOF 순위대로 변환을 시도하고 Python 모델과 ONNX 확률 차이를 검사한 첫 후보를 선택했습니다. 고정된 OOF 임계값으로 Holdout을 평가하고, 메타데이터와 식별자를 제외한 테스트 벡터도 생성했습니다.

대안은 최고 순위 모델만 변환하거나 분류 결과만 비교하는 것이지만, 변환 실패에 대응하지 못하거나 확률 차이를 놓칠 수 있습니다. 순위가 낮은 후보로 넘어갈 수 있다는 점과 Holdout 평가가 적격성 기준을 충족하지 못할 수 있다는 점이 트레이드오프입니다. 검증에서 실제 데이터의 최상위 변환 가능 후보는 랜덤 포레스트였고 Python과 ONNX 확률 차이는 허용 범위 이내였습니다. 다만 Holdout Brier Skill이 음수여서 모델은 **RESEARCH_ONLY**입니다. 집중 모델 테스트 39개가 통과했지만 Java parity와 지연 시간은 아직 검증되지 않았습니다.

## Task 5 — Java ONNX 추론과 parity

문제는 Python에서 만든 전처리와 ONNX 모델을 Java에서 실행할 때 입력이나 불량 확률이 달라질 수 있다는 점이었습니다. 그래서 Java에서 동일한 Feature 계약으로 float32 벡터를 만들고, 모델과 계약의 해시를 검증한 뒤 ONNX 입출력의 이름·타입·형상을 확인했습니다. 결측이 한도를 넘거나 추론이 실패하면 확률 없이 상태를 반환하고, **RESEARCH_ONLY** 모델은 확률이 있어도 경보를 내지 않도록 했습니다.

대안은 Java에서 별도 전처리 기준을 사용하거나 모델을 검증 없이 여는 것이지만, 입력 불일치나 잘못된 산출물을 놓칠 수 있습니다. 엄격한 검증과 결측 제한은 잘못된 예측을 막는 대신 입력이나 산출물이 계약과 다르면 추론을 거부하는 트레이드오프가 있습니다.

검증에서는 실제 모델 입력 10행의 float32 값 840개가 Python과 비트 단위로 모두 일치했고, Python ONNX와 Java ONNX의 불량 확률 최대 차이는 0.0으로 허용 오차 1e-5 이내였습니다. 세션을 연 뒤 인코딩부터 결과 처리까지 한 행을 측정한 평균은 0.0164918043ms, 중앙값은 0.014667ms, p95는 0.019167ms였습니다. 이는 Apple M1 Pro에서 워밍업 1,000회 후 10,000회 측정한 결과이며 지연 시간 기준은 적용하지 않았습니다.
